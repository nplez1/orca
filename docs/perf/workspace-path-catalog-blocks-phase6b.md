# Workspace path catalog blocks: Phase 6b measurement

The raw numeric samples are in [`workspace-path-catalog-blocks-phase6b.json`](./workspace-path-catalog-blocks-phase6b.json). The run used 100,000 generated paths per fixture, both deterministic profiles, seven warm runs per query class, and the same in-process query harness for `packed-folded` and `prefix-compressed`. The catalog footprint includes typed arrays, block bytes, postings, and the reserved 2 MiB decoded-block cache. This harness measures the **resident** form (in-process, 2 MiB decoded-block LRU); it does not exercise the disk-spilled query path, whose format and campaign are documented separately. The Phase 6a service baseline is [`workspace-path-index-matrix-phase6a.json`](./workspace-path-index-matrix-phase6a.json); its worker/service p95s are not directly comparable to this single-process catalog harness.

| Realistic shared-prefixes | prefix-compressed |        13.62 |       116.40 |            0.11 |            68.23 |            67.64 |            21.93 |
| Adversarial long/unshared | packed-folded     |        68.40 |        16.85 |            0.08 |            29.35 |            26.11 |             0.63 |
| Adversarial long/unshared | prefix-compressed |        66.85 |       414.26 |            0.12 |           412.54 |           407.01 |             1.97 |

Compression reduced measured retained bytes by 33.0% on this realistic 100k sample and 2.3% on the adversarial 100k sample. It did **not** pass the warm-latency gate: exact scan/decode was 4.9×–24.6× slower on the listed cells. Therefore the worker's normal published-catalog path remains `packed-folded` for **resident** queries. The resident prefix form is still not enabled as an admission fallback. The disk spill, by contrast, does use the same version-1 prefix block payloads: on disk the decode cost is paid once per block per exact scan, which is the intended lower-performance degradation, not a hot-path regression. See [`workspace-path-index-matrix-phase6b.md`](./workspace-path-index-matrix-phase6b.md) for the 1M spilled campaign and [`../reference/workspace-path-catalog-block-format.md`](../reference/workspace-path-catalog-block-format.md) for the implemented file format.

These samples were re-measured after the block checksum moved from a bit-at-a-time CRC to a 256-entry table (see the format reference). That change is decode/verify-only and format-preserving, so it reduced every prefix-block cell without changing the comparison: the earlier run measured prefix-compressed broad p95 at 276 ms realistic and 963 ms adversarial.

The 100k numbers do not by themselves establish a 1M capacity gain, and their process RSS samples were collected sequentially in one process, so their absolute peaks are not isolated build-peak claims. The production spill/build-run implementation and the isolated 1M admission/performance campaign now exist; they are recorded separately in [`workspace-path-index-matrix-phase6b.json`](./workspace-path-index-matrix-phase6b.json). That campaign is what establishes the Phase 6b exit row, not the resident prototype below.
